Alcance: semanas 10, 11 y 12 (v1.0 a v1.2). No se evalúan la refactorización (semana 13) ni las pruebas (semana 14), y el archivo de pruebas no se tuvo en cuenta en esta revisión. Las observaciones se basan solo en la guía, el README y los contratos.

Después de la revisión, cada fila del archivo queda en una sola bandeja: válidos + inválidos + errores = filas. Ningún registro se pierde y ninguno se cuenta dos veces. La distribución BAJO/NORMAL/ALTO de los válidos coincide también con la tabla del README (por ejemplo, temperatura: 151 / 225 / 152).

La interfaz no fallaba, pero mostraba resultados falsos. Con el código entregado, Streamlit mostraba 2394 registros «recibidos» para los tres archivos (son 1904), 0 errores técnicos y una tabla de inválidos con solo la columna de motivos, sin id, tipo ni valor. Un programa que no se cae no es necesariamente un programa correcto.

Causa común: código pegado debajo de la plantilla

En cinco de los siete archivos de los estudiantes (errores.py, procesamiento.py, fuentes_memoria.py, lectores.py y carga_datos.py), la solución se agregó debajo de la plantilla sin borrar la versión original; en validaciones.py se repitió una constante. Quedaron funciones, clases, imports y docstrings repetidos. Python no avisa: cuando un nombre se define dos veces, la segunda definición reemplaza a la primera en silencio. Esto produjo el error más grave del proyecto (dos ciclos for en la misma función, B-1) y hacía muy difícil saber qué código se ejecutaba realmente.

Convenciones de este informe

Crítico rompe la ejecución o produce resultados falsos. Alto incumple un requisito de la guía o deja pasar datos incorrectos. Medio afecta el contrato o la mantenibilidad. Bajo es una mejora de robustez o de estilo.

En el código, cada cambio lleva el comentario # REVISIÓN (X-n) con el mismo identificador que usa este informe (por ejemplo, # REVISIÓN (B-1)), para que puedan buscarlo con Ctrl+F. El trabajo de los estudiantes se conservó: se corrigió y se completó, sin reescribirlo desde cero. Los TODO originales se mantienen como referencia.

A-3Un NaN no se consideraba vacíoAltoS12

Observación: str(nan) es "nan", que no está en blanco, y float("nan") no falla. Por eso una celda vacía de Excel pasaba la revisión de vacíos y terminaba rechazada como «fuera del rango lógico: nan». Era el mismo problema con un motivo distinto según el archivo.

Después
def _esta_vacio(contenido):
    if contenido is None: return True
    if isinstance(contenido, str) and contenido.strip() == "":
        return True
    # NaN es el único valor distinto de sí mismo
    return isinstance(contenido, float) and contenido != contenido
